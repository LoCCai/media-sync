# 目标：补齐 0088 遗留的操作者可见缺口

## 为什么需要这次执行

[0088](../0088-code-review/verification.zh.md) 修复了 26 个缺陷，但有三条面向操作者的发现因被判为 NIT 或 RISK 而没有修。它们并不是外观问题：每一条都让真实状态对部署者不可见。本次执行收拢它们，且不触碰任何已冻结的平台行为。

1. **四个平台的续跑延迟在任何界面都看不到。** 操作者要把 `/api/v1/settings` 与 `doctor --deep` 对照 supervisor 的环境，才能证明两个进程以相同节奏扫描。这两个界面只报告了 B 站、小红书、抖音和快手。微博、贴吧与知乎——正是那九个构造点里策略缺失的平台——完全不可见，而这恰好就是那个接线缺口一直没被发现的原因。
2. **概览把有界窗口当成总量呈现。** 任务是 `limit=12`、资产 `limit=200`、内容 `limit=50` 取的，而 KPI 卡片从这些数组推导"待处理任务"和"已归档资产"。40 个任务的队列显示 12；5 000 个资产的库显示 173。数字对窗口是对的，对问题本身是错的。
3. **所有非调度类操作行都显示"已有白名单摘要"。** 只要 `safeOperationResult` 返回投影，单元格就打印这句话，无论该操作是下载、导出还是登录，因此一次成功的下载与一次成功的登录一眼看过去没有区别。

## 保持不动的内容

- 不改变任何平台的游标、停止原因、选流或交付行为。本次执行只涉及 API 与控制台**展示**什么。
- 不新增任何可能携带密钥的字段：新增的值是 `Settings` 里已有的整数延迟，已经过校验，也已被部署交接对照。
- 部署、登录与每一次真实请求按 [0087](../0087-operator-canary/qualification.zh.md) 保持 `NOT_RUN`。
