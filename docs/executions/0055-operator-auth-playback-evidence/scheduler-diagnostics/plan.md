# Frozen scheduler diagnostic plan

1. Commit these bilingual records before implementation. Retain historical canary error schema_invalid; do not backfill an invented cause, complete its running Run, restart supervisor or retry.
2. Add exactly three closed terminal/circuit-affecting classifications, preserving the old schema_invalid failure semantics: scheduler_heartbeat_failed, scheduler_heartbeat_storage_busy, scheduler_finalize_failed. No retry policy, busy timeout, lease duration, circuit accounting or transaction change.
3. Classify only the caught ordinary heartbeat exception. SQLite busy/locked requires SQLAlchemy OperationalError with sqlite3.Error orig and a strict integer native sqlite_errorcode whose base code is SQLITE_BUSY or SQLITE_LOCKED; never inspect error text, SQL, paths or arbitrary exception attributes. Everything else gets generic heartbeat_failed. Lease loss and cancellation remain their existing control paths; cancel and join the handler before publication.
4. Separate only the actual _finalize call boundary in run_once from context/invoke/result validation; catch its ordinary exceptions as finalize_failed. Parameterize the existing fail-closed recovery with that fixed code, retaining its successful-Run authority check and all lease/cleanup fencing. An unavailable durable store can still leave a fenced Job without a persisted diagnostic; no synthetic failed Run or secret-bearing fallback is permitted.
5. Expose optional last_error_code in the shared API/CLI scheduler Job projection and error_code in CLI worker output. Only exact recognized classify_failure vocabulary and failure/wait/retry/fenced states are eligible; missing/unknown/contradictory success yields null, never mapped unknown text. No SQL/exception/body/lease fields, additional queries, batch Operation schema changes or database migration. Old API clients may ignore the additive field; new Web accepts old responses without it.
6. Web uses a fixed code allowlist and Chinese explanations in Job list/detail, not raw field iteration for the new value. Say what stage failed and how to inspect it; schema_invalid remains historical/ambiguous, SQLite busy does not imply corrupted DB, and none of these codes proves invalid Cookie. Preserve the prior Worker/business-result distinction and non-scheduler flows.
7. Tests: exact failure tuples, typed and forged busy exceptions, actual file-backed SQLite contention using a second connection and a short test-only busy timeout; release before finalization and prove handler cancellation/join and no false success. Cover already committed Run success, transient/permanent finalize errors, lease loss/cancellation/cleanup precedence, unknown/secret sentinel projection, old/new UI response shapes and unchanged retry semantics.
8. Run focused and broader scheduler/API/CLI/Python and serial Web gates, static/docs/upstream checks, independent review, bilingual commits/push verification. Live capture remains FAILED and new diagnostics NOT_RUN on production until operator deployment and separately authorized canary. Next: bounded Bili creator collection and pasted-Cookie validation/save/reuse, then remaining live platform/archive/playback gates.
