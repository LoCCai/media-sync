## 范围与已核实问题

七平台登录／订阅／抓取与 Emby/Jellyfin 原定目标不变。冻结目标／计划保留为历史契约；本补充计划调整执行顺序，不降低安全要求。当前 main 是开发集成检查点，不是可以完整升级使用的发布版。本次收尾不授权扩展新平台、媒体形状或运维子系统。

静态检查确认前端缺少 login/session/CSRF、镜像运行 UID 1000、Compose 使用文件型凭据挂载，以及 `db init` 先于 `serve`。在普通 rootful Linux 权限下，root 所有的 0600 源文件可能对运行用户不可读；这是有条件风险，不是已观察到的用户主机故障。证据读取与资格 v3 现已实现，更新了旧核查中的这一待办。当前发布的人工确认与平台资格仍相互独立，绝不代表播放遥测。

## 部署与升级边界

凭据源文件继续受限，并让所有者／读取权限与实际映射后的运行身份一致。不得改成所有人可读、盲目递归更改所有权，也不假设 Compose secret uid/gid/mode 会重映射权限。[部署指南](../../deployment.zh.md)已补充绕过普通 entrypoint 的最终镜像手工读取预检。Rootless／user namespace 映射需按主机实际验证。

当前 entrypoint 仍先迁移，再由 `serve` 校验鉴权。服务启动失败不代表数据库未变；升级前须备份，通过覆盖 entrypoint 先预检，并遵守含数据 revision-0008 的降级拒绝。自动启动／迁移前校验仍属于 P0 待实现，不能声称已修复。

## 真实性与产品语义

平台资格是某版本／平台的真人验收记录；作者证据是某次发布／远端观察对应的人工确认。发布变化可以让这条确认 stale，但不会改写平台资格。身份匹配或账本 POST 都不能证明视频实际播放。

严格区分三个概念：提交媒体库刷新（只确认接受）、核验首次入库（原先不存在的作者变为唯一匹配）、核验新增内容（后续按发布条目实现）。既有 absent-to-match 不是通用增量核验。API/CLI 大文件治理放在首次真实闭环之后，只抽离持续修改部分的共享构建／业务入口，不安排架构重写。
