# 计划：六方向独立代码审查

状态：**已执行。** 六个只读审查者并行运行；每条发现在改动代码之前都重新核实过。

## 1. 冻结基线

确认代码树在 `830b4d0` 干净、既有门禁通过，这样后续失败可归因于修复而非起始状态。

## 2. 按互不重叠的范围分派

六个审查者，各一个范围（见 [goal.zh.md](goal.zh.md)），全部被要求通过阅读生产代码与运行定向探针来证实结论，并把"已核实"与"无法确认"分开。

最关键的是那条否定式指令：**不要信任此前的收尾结论。** 0085/0086 的交付测试直接驱动仓储，这恰恰是"缺一个 publisher"或"丢一个覆盖字段"能活着穿过绿色套件的原因。

## 3. 改代码前重新核实每条发现

对每条结论：读被引用的代码、用探针或聚焦测试复现失败，然后才决定。有两条结论在此阶段被驳回，使记录对"到底哪里错了"保持诚实。

## 4. 按依赖顺序修复

1. **先状态机**（微博停滞计数、贴吧跳页与空页、知乎回放与位移语义、微博 `declared_total` 边界），因为捕获 shim 与交付迁移都是照着它们写的。
2. **再捕获 shim**（知乎循环形状、贴吧/知乎回调、空页分类），对照修正后的单元语义。
3. **再生产接线**（覆盖字段透传、知乎 publisher、`source_run_id`、每个构造点的续跑策略、守卫元组）。
4. **再摄取边界**（按平台记录上限）。
5. **再安全**（WAL 的 `secure_delete` 覆盖、注入连接的 pragma、`db status` 使用托管引擎、收窄媒体子进程环境）。
6. **最后前端**，因为其中三条发现依赖后端必须先开始正确发送的载荷字段。

## 5. 每个修复都用"先失败"的测试钉住

每个功能性修复都配一个在修复前代码上会失败的回归测试。对于接线类修复（知乎 publisher、修订白名单），钉法是枚举式测试：遍历平台集合或迁移集合，漏掉一个成员就失败，使下一个平台无法悄悄重复同样的遗漏。

## 6. 重跑完整门禁

Python 完整套件、Ruff lint 与 format、strict mypy、文档链接、钉定上游，以及全部四个 Web 脚本。记录确切计数。

## 7. 诚实记录

写 [verification.zh.md](verification.zh.md)，分成三段：已修、核实后驳回、已报告但未修。第三段是强制的——一份悄悄丢掉未处理发现的审查报告，比不审查更糟。
