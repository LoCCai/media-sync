# 目标：六方向独立代码审查

## 为什么需要这次审查

0084–0087 四次执行都是作者用自己写的测试验证自己的代码。这是一种很弱的验证形式：与代码同源误解的测试照样会通过。尤其是 0085 与 0086，是在"直接调用新仓储"的测试支撑下被宣布"本地完成"的——恰好绕过了接线可能缺失的生产路径。

因此本次执行请六个范围互不重叠的审查者，在**不信任此前收尾结论**的前提下攻击 `830b4d0` 的代码树，并通过阅读生产代码与运行定向探针来证实结论。

## 审查范围

| 审查者 | 范围 |
| --- | --- |
| 创作者链 | 微博/贴吧/知乎状态机与捕获 shim，对照四个更早的参考实现 |
| 迁移 | 0018/0019/0020 DDL 与 ORM 模型、摄取事务边界 |
| 媒体 | 请求 profile、URL 校验、选流排序、下载续传、探针/封装 |
| API/CLI | 订阅载荷、`ingest_*_bounded` 分发、策略接线、manifest 往返 |
| 前端 | Svelte 状态/异步/错误处理，以及与 API 的载荷/类型一致性 |
| 安全 | `secure_delete` 覆盖、密钥可达性、路径安全、auth/CSRF、子进程环境 |

## 给审查者的规则

- 通过阅读生产代码核实；通过的测试本身不算证据。
- 只报告已确认的问题，每条都要给严重度、文件:行号、具体失败场景与修复建议；把"已核实"与"无法确认"分开。
- 不报告风格意见，不提重构建议。
- 不编辑、不提交、不跑完整套件。

## 交付物

一份记录，包含：

1. 已修缺陷清单，以及每条缺陷避免的具体故障；
2. **核实后被驳回**的结论，使记录不夸大发现；
3. 真实但**刻意不在本次修复**的缺陷及原因，使它们成为下一次执行的范围而不是被静默丢掉；
4. 修复后代码树的完整门禁结果。

## 不在范围

- 对 0076/0081/0083（小红书/微博 URL 校验、快手主机允许列表、抖音选流上限）的任何行为改动：各自需要独立执行并重新推导钉定上游事实。
- 部署、真人登录或任何平台请求。按 [0087](../0087-operator-canary/qualification.zh.md)，每一行真人工作保持 `NOT_RUN`。
