# Next slice: automatic creator profiles

Status: **design draft, not implemented or live-tested**. This records the next mandatory item after removal/report delivery. Freeze a separate goal/plan before changing the profile protocol or schema; this document is not evidence that existing local preview contacts a platform.

## Source findings

At locked MediaCrawler `d6f7c5bb906b6dac40ddf343ef9e26438a3de092`, Bili client `get_creator_info` is a single-profile request, but core `get_creator_details` continues into dynamics. Never invoke the latter for profile lookup. Other platforms expose single-profile methods, but still require independent identity/authentication/field/avatar contracts and qualification.

Current `Author` is shared by platform/remote ID across accounts. `AuthorRepository.upsert` overwrites name, handle, profile and avatar, including missing values. Writing a remotely retrieved nickname straight into this row can change another account's display or disappear on the next ingestion. Saved-session and content runners already share `_AccountFileLock`. SafeHttpClient pins validated DNS endpoints but permits redirects by default; a first-URL avatar check alone is insufficient.

## Proposed bounded delivery

1. Start with Bili saved-session single-profile capability. A dedicated isolated runner performs noninteractive authentication and exactly one creator-profile call; allow only bounded authentication/WBI setup requests. No QR fallback, subscription creation, content/dynamics/comment crawl, scheduler work or login-state promotion. Suggested hard total deadline: 45 seconds, no automatic retries, immediate account-busy outcome. Hold the shared account lock until the entire child tree exits; retain checkout/module-origin verification, private stdin and fixed output framing.
2. Reuse durable Operations with a dedicated creator-profile kind and exact account target. Proposed POST `/api/v1/accounts/{account_id}/creator-lookups` and exact GET `/api/v1/creator-lookups/{operation_id}` use closed inputs/results and existing authentication/CSRF. Bind account/platform/stable creator ID, frontend generation, backend monotonic generation and operation ID. Before persistence, recheck lease/cancellation, current credential/auth snapshot and generation. Frontend identity/epoch checks prevent A→B→A and late-response overwrite. Candidate errors never clear prior successful profile data.
3. Add an account-scoped profile cache keyed by account/platform/creator and a separate subscription local alias. Preserve last successful nickname, canonical homepage, upstream SHA, time and revision; avatar has its own revision/time. A scoped, expiring profile receipt may bind subsequent creation to server-held data instead of trusting client-supplied remote names. Preserve existing Author naming/export paths in the first slice; migrate existing labels as local notes, not verified remote names. Ordinary ingestion must not erase the separate successful profile. Nickname success plus avatar failure may update nickname while retaining an explicitly old avatar.
4. Keep CSP unchanged. An authenticated same-origin avatar route accepts only profile ID/revision, never an arbitrary URL. Bili's proposed closed HTTPS hosts/path must be verified against fixtures/live evidence; unknown forms yield no avatar. Disable redirects for the first slice, send no cookies/auth, reject private DNS/IP, userinfo and unexpected ports. Suggested caps: 2 MiB, eight million pixels, single-frame JPEG/PNG/WebP, ten-second fetch limit; isolated bounded decoding and controlled static re-encoding, no SVG/HTML. UUID/hash-derived cache paths, nofollow/regular-file checks, proper MIME/nosniff/CORP and private caching remain mandatory.
5. Preserve current local syntax preview and expose remote lookup as a distinct action. The UI should show platform nickname, local alias, observation time, loading/error and retained-old-profile/absent-avatar states. Once the precise account and stable ID are valid, one bounded automatic lookup can populate the form; never automatically retry endlessly or call local preview a remote query.

The remaining six platforms and Cookie-mode lookup remain required extensions, not advertised as implemented by the Bili saved-session slice. Cookie mode additionally needs a private value-change fence when a secret reference stays the same but its contents change. Pasted-Cookie login validation/persistence is a separate accepted requirement and is not satisfied by this lookup.

## Required verification before qualification

Trap every content/dynamics/comment method; count the exact single-profile call. Reject mismatched account/platform/creator/generation/receipt and cancellation/credential races. Prove lookup/login/crawl/detail share one lock until child-tree cleanup. Fail expired authentication without QR or LoginSession mutation. Test fresh/upgrade migration, alias/profile preservation through ingestion and failed lookup, unchanged existing export paths, avatar SSRF/redirect/rebinding/size/slow-stream/decode/path attacks, and synthetic browser late-response handling. Only then perform a separately authorized real Bili single-profile check; offline checks are not platform PASS.
