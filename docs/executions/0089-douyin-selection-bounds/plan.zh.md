# 计划：收䱲 0088 延后的两个抖音选流缺口

状态：**已执行。**

## 1. 改边界前先重新推导钉定事实

再读 `.upstream/MediaCrawler/store/douyin/__init__.py:122-139`：钉定 store 把
`play_addr_h264` → `play_addr_256` → `play_addr` 依次扁平化，取 `url_list[-1]`，
并要求 `len(url_list) >= 2`。它从不读 `bit_rate[]`，这正是为什么只有 0083 自己的排序
才能表达更优流。

## 2. 只改证据支持的部分

- **条目上限。** 把凭空定的 8 换成 32（对“画质×编码”声明而言是现实上限），
  超出仍然抛错，因此无界的服务端数组保持被拒绝。把理由写在代码里，
  使下一个读者不会把它“简化”回去。
- **拒绝逗号。** 在 `validate_douyin_media_url` 的拒绝字符中加入 `,`，
  因为 shim 写入的是它自己的读取器会按逗号拆分的字段。
  不要放宽 `_dy_url_list`：该函数被笔记图库与其他媢体字段共用，
  在那些地方逗号确嫦就是列表分隔符，放宽会接受夹带的第二个 URL。

## 3. 用“先失败”测试钉住两者

- 12 项（4 × 3）载荷必须排序到最大流；改动前它抛 `douyin_media_field_invalid`。
- 33 项载荷必须仍然抛错。
- 含逗号的 URL 必须在选流时就被拒绝；改动前它归一化为 `kind=text` 且零资产。

## 4. 不动需要操作者的三条发现

快手 CDN 允许列表、小红书明文 `http`、动画图片——它们要么在仓库里没有可推导的证据
（快手：全树零个真实主机名），要么改动的是此前已取得资格的能力
（小红书已文档化并测试为 HTTP/HTTPS）。在此记录它们才是正确的收尾；凭空夹一个值只是猜。
