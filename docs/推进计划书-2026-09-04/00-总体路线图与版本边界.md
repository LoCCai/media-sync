# media-sync 总体路线图与版本边界

## 1. 0050 前评审基线（历史快照）

> 2026-09-05 状态校准：下列最初阻塞项 1–3（checkout 校验、深度就绪、通用 Web 错误）已由 0047-d1/d2 与 0050 后续修复闭环，条目 4 已由 0052 交付。Execution 0053 已完成条目 5 的内容/资产安全浏览切片；0054-A 已交付数据库发布链授权的只读媒体库树、单一环境托管 Emby/Jellyfin 配置、连接探测/Library 发现/定向刷新接受及三分资格，并以 2620 passed、3 skipped 完成冻结验证。0054-B 尚待另行冻结；当前权威状态见 [`../status.zh.md`](../status.zh.md)。阶段 B 的 Linux 持久性/恢复/进程证据和阶段 C 真人金丝雀仍是 P0，条目 6 继续属于后续控制面工作。

media-sync 已经拥有以下核心能力：

- 七平台账户、作者和订阅的统一领域模型；
- MediaCrawler 外部进程桥接、许可证门禁与隔离浏览器 profile；
- 增量同步、持久调度、租约、fencing、恢复和重放；
- 可续传、安全校验的媒体下载；
- SHA-256 内容寻址归档；
- Bilibili progressive、DASH、FLV、多分段等冻结形状；
- 图文、图集、视频和混合内容的 Emby/Jellyfin 确定性导出；
- 0054-A 的媒体库只读检查、受限 Emby/Jellyfin 定向刷新与资格事实投影；
- FastAPI REST 接口与一个可执行基础操作的嵌入式控制台；
- Docker 本地构建、SQLite 持久状态和 supervisor 模式。

该历史评审时的阻塞不是缺少更多媒体类型，而是：

1. 严格 checkout 校验失败，导致全部真人登录在启动前被拒绝；
2. `health`/`ready` 只说明进程和数据库正常，不能说明 MediaCrawler 可以工作；
3. Web 只能看到通用 `account_login_configuration_invalid`，无法说明具体是哪一项预检失败；
4. 后台操作仍以进程内注册表为主，服务重启后操作历史不可追溯；
5. 内容、资产、归档和 Emby 结果缺少完整浏览与筛选界面；
6. 当前无鉴权服务被发布在 `0.0.0.0:8632`，操作面暴露范围过大。

## 2. 产品目标重新表述

media-sync 不应被定位为“带页面的爬虫”，而应定位为：

> 面向个人自托管场景的多平台创作者订阅、内容归档、媒体验证和 Emby/Jellyfin 发布系统。

这意味着 Web 后台必须围绕“运营闭环”组织，而不是围绕内部命令组织：

```text
账户授权
  → 添加作者订阅
  → 定时发现内容
  → 生成下载任务
  → 下载/验证/归档
  → 导出媒体库
  → 重扫与抽样播放
  → 失败诊断、恢复与审计
```

## 3. 版本边界

### 3.1 v0.1.0-rc1 必须具备

- Linux 阶段 B 全绿；
- `mediacrawler doctor` 明确通过；
- Bilibili 与小红书至少达到 Supported；
- 真实增量和无变化重放分别通过；
- Emby/Jellyfin 真机重扫与抽样播放通过；
- 控制台能明确显示所有预检项，而不是只显示一个通用错误；
- 操作失败不能假绿；
- 对外发布仍使用“七平台适配框架，实际资格见矩阵”的表述；
- 端口默认回环或明确受保护的可信网络。

### 3.2 v0.1 不应被完整 Web 重构阻塞

现有控制台已经足以驱动阶段 B/C，只需要补足：

- 深度预检页；
- 具体错误码；
- 运行时和 checkout 信息；
- 操作状态与最近失败；
- 对当前危险暴露方式的醒目提示。

这部分可以作为 `0047-d1/d2` 的最小运维修复完成。

### 3.3 v0.2 目标

v0.2 承担完整 Web Console v2：

- 现代 SPA；
- 账户登录工作台；
- 作者与订阅管理；
- 持久任务队列；
- 实时日志和操作事件；
- 内容/资产/媒体库浏览；
- Emby/Jellyfin 联动；
- 单操作者访问控制；
- 设置、备份、恢复、升级和支持包；
- 0043 弹幕/字幕 sidecar。

## 5. 不应立即推进的方向

在 P0 闭环前暂停：

- 新平台；
- 新内容类型；
- 通用转码；
- 多用户和云端多租户；
- 分布式队列；
- Redis/Kafka；
- PostgreSQL 强制迁移；
- 公网 SaaS 化；
- 复杂可视化图表。

当前单主机 SQLite + 模块化单体仍然适合产品目标。真正需要改造的是控制面和可观测性，不是盲目拆微服务。

## 6. 关键决策

### 6.1 前端参考 bili-sync-up，但不复制其领域模型

可借鉴：

- 清晰侧栏；
- 仪表盘；
- 视频源/内容管理；
- 实时任务队列；
- 日志中心；
- 设置中心；
- 响应式布局和状态徽章。

不能照搬：

- 单平台 Bilibili 源模型；
- 仅视频对象；
- 与 media-sync 租约/fencing 不一致的队列操作；
- 将原始 Cookie 直接交给页面；
- 对七平台差异视而不见的统一表单。

### 6.2 FastAPI 保持唯一业务入口

Web 不能直接操作 SQLite，也不能另造一套下载、调度和导出逻辑。所有动作必须复用已有 application service。

### 6.3 先持久化操作，再做漂亮队列

如果操作仍只在内存里，页面再漂亮也无法解释服务重启前发生了什么。持久操作和结构化事件应先于复杂 UI。

0052 已完成这一顺序：持久状态机和事务事件 cursor 先于 Jobs 路由任务中心落地。冻结公开契约不返回 raw idempotency key、requester、lease、revision 或指纹；Operation Event 不是通用文件日志，支持包是窄化 JSON 聚合，不是 ZIP/主机/配置/进程导出。既有 supervisor Job 不声明已全部统一为 API Operation，订阅 pause/resume/delete 审计后移到 0055，真实 Jobs 路由浏览器 interaction/E2E 属于后续质量债。

## 7. 总体验收定义

项目达到“可长期自托管”至少需要：

- 能从页面判断系统是否真的具备登录条件；
- 任一失败能定位到固定错误码和阶段；
- 服务重启后任务、操作和失败历史仍存在；
- 账户、订阅、内容、资产、归档和媒体库之间可追溯；
- 所有破坏性操作有确认、幂等和审计；
- 无 Cookie、签名 URL、二维码、密码进入日志或普通 API；
- 操作者能够完成备份、恢复和升级；
- 平台资格状态基于真实证据而不是离线测试数量。
